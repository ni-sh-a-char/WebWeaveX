# JAVA_EXTRACTION_RISKS

**Phase 7 — divergence, non-determinism, network, replay, and runtime-state risks for the
extraction subsystem.** Each risk is rated **Likelihood × Impact** and carries a concrete
mitigation. Risks are ordered by how much they constrain the implementation order.

---

## R-1 — The lxml ⇄ html.parser parser-dialect split *(BLOCKER, High×High)*
The `extract` family parses with **`BeautifulSoup(text, "lxml")`** (`core/extract/html_extractor.py:7`,
`core/security/safe_parser.py:8`), whereas `core/browser`, `core/dom`, `core/extraction`,
`core/adaptive/semantic_anchor` parse with **`"html.parser"`**. The two parsers diverge on
malformed-HTML recovery, implicit tag insertion (`<html>/<head>/<body>/<tbody>`), whitespace
in `get_text(separator=…)`, and attribute handling. The Dart effort certified an
**`html.parser`-parity Soup engine** — that engine is **not** byte-equivalent to lxml.
- **Impact:** Java needs **two** independent Soup engines to fully close Class C. Reusing
  one for both will silently diverge on adversarial HTML.
- **Mitigation:** Treat L3a (lxml) and L3b (html.parser) as **separate** sub-projects (DAG
  item 6 vs 7). Port the html.parser engine first by transcribing the certified Dart rule
  catalogue (it already exists, per project memory); build the lxml engine against
  libxml2's documented HTML recovery rules with a large adversarial-HTML vector set. **Do
  not** start either until the Class-A READY slice has shipped — neither blocks it.

## R-2 — `extract_repository` embeds absolute paths + OS separators *(High×High)*
`core/repository/repository_ingestion_engine.py:66,75` stores `"path": str(file)` and
`"root": str(root)`. `str(pathlib.Path)` yields `\` on Windows and `/` on POSIX, and the
absolute prefix is machine-specific. A golden vector generated by Python on CI (`/…/fixture/a.py`)
will **never** byte-match a Java run on Windows (`…\fixture\a.py`).
- **Mitigation:** the parity harness must (a) commit a fixture repo under
  `java/src/test/resources/parity/repo_fixture/`, (b) invoke `extract_repository` with a
  **relative** root, and (c) define a canonicalization both sides apply before compare —
  strip the root prefix and normalize separators to `/`. This makes parity "byte-exact after
  a declared canonicalization," which must be **documented** (it is weaker than the raw
  byte-exactness of Class A). Until governance accepts this, keep `extract_repository`
  behind the Class-A slice.

## R-3 — `MAX_FILES=100000` truncation happens *before* the sort *(Low×Medium)*
`repository_ingestion_engine.py:48-49`: the `rglob` walk `break`s at 100k **unsorted**
entries, then sorts. For repos >100k files, *which* 100k survive depends on `rglob` order
(non-deterministic across OSes). Below the cap (the normal case) it is fully deterministic.
- **Mitigation:** replicate the exact truncate-before-sort semantics in Java; keep parity
  fixtures well under 100k files so the edge is never exercised by a vector; document the
  >100k case as an accepted, mirrored non-determinism.

## R-4 — `Counter.most_common(1)` tie-break ordering *(Medium×Medium)*
`repository_language_detection_engine` and `core/extract/repository_intelligence` compute
`primary_language` via `collections.Counter.most_common(1)`. On a count tie, CPython returns
the **first-inserted** key; insertion order here = file-sorted order. Java `HashMap`/streams
do not preserve this.
- **Mitigation:** in Java, build the counter over the **already-sorted** file list using an
  insertion-ordered map (`LinkedHashMap`) and select the max with a **stable** reduction that
  keeps the first-seen key on ties — byte-matching CPython's tie-break.

## R-5 — The `extract` family's bespoke determinism stack *(High×High, scoped to Class C)*
`extract` output embeds a fingerprint from `dumps_deterministic`
(`core/serialize/deterministic_serializer.py`) + `fingerprint_v3` = the `kaalka_encrypt_bytes`
XOR/position cipher (`core/crypto/kaalka_engine.py`) — **distinct** from the certified
`stable_serialize`/`compute_kaalka_hash`. `dumps_deterministic` coerces integral floats to int
**before** `.15g` formatting (an explicit cross-language contract at lines 25-33), and applies
NFC.
- **Impact:** any Class-C output is non-byte-exact until **both** primitives are ported and
  independently vector-tested. Mixing them up with the existing Kaalka hash will diverge.
- **Mitigation:** port `dumps_deterministic` and `fingerprint_v3` as **standalone** L1b
  primitives with their **own** golden vectors **before** wiring any `extract` output.
  Class A/B do **not** hash, so this risk does not touch the READY slice.

## R-6 — Python `re` vs Java regex dialect drift *(Medium×High, pervasive in Class C)*
Class C leans heavily on regex (`markdown_extractor`, `code_extractor`,
`dependency_extractor`, `architecture_extractor`, `repository_intelligence`,
`metadata_extractor`, and the repository `ROUTE_PATTERNS`/`IMPORT_RE`). Divergence points:
`\w`/`\b`/`\s` Unicode semantics (Python `re` is Unicode by default; Java needs
`UNICODE_CHARACTER_CLASS`), `^`/`$` multiline anchoring (`re.MULTILINE` ⇄ `Pattern.MULTILINE`),
`.` with `re.DOTALL`, non-greedy `(.*?)`, and `[^\s\)]`-style classes.
- **Mitigation:** port each regex with an explicit flag-by-flag mapping and a per-pattern
  vector (incl. Unicode inputs). Prefer transcribing the regex **verbatim** and adjusting only
  flags; never "rewrite for Java idiom."

## R-7 — `heal_selector`'s hidden html.parser edge *(Low×Medium)*
`heal_selector` is otherwise pure, but `build_semantic_anchor`
(`core/adaptive/semantic_anchor_engine.py`) parses the caller-supplied `html` string with
`html.parser`. Deterministic given the string, but it is a **Soup** dependency.
- **Mitigation:** scope the Class-A `heal_selector` slice to vectors where the `html` argument
  is **empty or trivial** (so no real parse occurs), proving the selector logic; defer
  full-HTML `heal_selector` vectors to the L3b html.parser engine. (This keeps `heal_selector`
  genuinely READY without smuggling a Soup dependency in.)

## R-8 — Unicode normalization & code-point ordering *(Medium×High)*
Every layer sorts with `sorted(...)` / `sorted(set(...))` and normalizes (NFC in
`normalize_output`/`dumps_deterministic`; NFKC in the L0 foundation). Java sorting is
UTF-16/`char`-based; Python sorts by Unicode **code point**. They diverge on astral-plane
characters (surrogate pairs) and on combining-mark ordering after normalization.
- **Mitigation:** reuse the **already-certified** `Normalization.codePointCompare` from the
  Java foundation for every extraction sort; never use natural `String.compareTo`. Include
  astral-plane and combining-mark strings in every slice's vectors.

## R-9 — Float / numeric canonicalization in IR payloads *(Medium×Medium)*
Document/repository IRs carry numeric fields (sizes, counts, confidences). Python emits via
`repr(float)` / `.15g` / int-coercion; the Java foundation's `PyFloat` handles `repr(float)`
but the extraction layer's `dumps_deterministic` `.15g` path (R-5) is a **different** formatter
for the Class-C path.
- **Mitigation:** for Class A/B (no `dumps_deterministic`), confirm all numerics are ints or go
  through canonical JSON; add float-edge vectors (`1.0`, `0.1`, large/small magnitudes,
  negative zero). For Class C, gate on the R-5 `.15g` primitive.

## R-10 — Network at the entry boundary (`extract`/`crawl`/`extract_web`) *(High×High for full API)*
`fetch_sync`/`fetch_async` (`requests`/`httpx`, retries on HTTP 429) and `groq_complete`
(env key + live API) make the **full** `extract(url)`, `crawl`, `extract_recursive`, and
`extract_web` non-deterministic. Policy §5 forbids stubbing them in `src/main` to fake parity.
- **Mitigation:** the **non-URL / no-LLM** path of `extract` is the parity-certifiable surface
  (deterministic via `fetch_raw`). Prove only that path; leave the URL/LLM/crawl/browser
  surface `⬜ Planned` (it cannot be a stub-free Complete). Do **not** introduce an injectable
  fetcher into `src/main` purely to satisfy a vector — that is a placeholder.

## R-11 — Live browser / OS state (Class D/E) *(by design, not parity-certifiable)*
`extract_web` (Playwright `render_page`), `extract_infinite_scroll` (`page.evaluate` scroll),
`capture_dom_mutations` (MutationObserver), `capture_websocket_frames` (live WS), and
`extract_native`/`run_native_cognition` (`sys.platform` probes + electron CDP) depend on state
that cannot be reproduced byte-identically across hosts.
- **Mitigation:** for the Class-D **transform-cores**, port and parity-prove the
  snapshot→events mapping against committed fixture pages (these are honestly provable). Mark
  the live/platform *source* APIs **Deferred (permanent)** in the matrix with an explicit
  reason, mirroring the Dart "platform-bound Deferred ceiling." Never claim Complete for a
  live-source API.

## R-12 — Replay / runtime-kernel coupling *(verified ABSENT — low risk, recorded)*
A natural worry is that extraction feeds the replay/reconstruction subsystem. **Verified
false** for the `core/extract` and `core/documents`/`core/repository` closures: they do **not**
import `core.kernel`, `core.replay`, `core.ir` (runtime), or `core.determinism`. `extract_web`
*does* build runtime graphs / memory / replay stores, but those primitives are already certified
in Java (L0) and `extract_web` itself is Class C+D anyway.
- **Mitigation:** none needed for the READY slice; recorded so a future reader does not
  re-investigate. Re-verify if `core/extract` imports change upstream.
